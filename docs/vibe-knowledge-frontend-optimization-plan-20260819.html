01 / DECISION
无需后端配合

前端自身问题

单 reducer 收口、SSE 连接状态、错误视觉、来源折叠、加载状态、信息栏跳转、上传进度和响应式布局。

真实 SSE 已确认

语义内容来自后端

“查找现行知识”、过程旁白、stable revision、答案、CanonicalRef、DTA/Trace 和成功终态都已在正式事件中出现。

一项需要后端确认

成功与 incomplete 的关系

外层 action 显示“成功 / 完成”，内部 canonical_tool_result 却是 incomplete、has_more=true；前端不能自行改写其业务含义。

真实 SSE 实证 · 2026-08-19

用户提供的正式 /api/vibe/foundation/turn/stream 响应包含 turn_started → process items → answer → sources → event_saved → done。 “查找现行知识”由后端以稳定 item_id 提供，并从 running revision 更新到完成 revision； DTA、trace_id、7 条 CanonicalRef 和 completed terminal 均来自 Canonical Journal。

明确告知机制

开发中一旦遇到后端配合项，将提供：缺少的字段或接口、影响的用户体验、最小后端需求、前端为何不能安全兜底。在你确认前，不扩展到后端。

建议拆成 7 个独立 Checkpoints

每项都能单独评审和验收。C0 是建议首先执行的优化，不涉及后端修改。

05 / PLAN
C0

Canonical 单 owner 收口

已完成前端实现，待真实失败、取消、重连与 replay 场景验收；第二套实时业务解释路径已删除。

文件范围

harness.ts、turnProtocol.ts、useProcessTurn.ts、knowledge/index.vue、协议合同测试

风险 / 体量

高；约 300–600 行触达，目标净删除 legacy 分支

后端配合

无需 不改变请求与事件含义

  • 实时、event_saved、running replay 使用同一 reducer/read model。
  • stable item revision 只覆盖同一 item，不再追加重复旁白。
  • “查找现行知识”等过程内容只读取后端 title/summary/status，前端不补写业务文案。
  • 删除成功型 synthetic answer；失败时保留真实未知状态。
  • 验收重点：合法 answer → sources → event_saved → done 顺序不闪烁、不丢来源。
C1

断流、取消、重连与 replay

已完成前端实现，待真实断流与 running snapshot 验收；连接结束不会再自动生成成功答案。

文件范围

harness.ts、turnProtocol.ts、knowledge/index.vue

风险 / 体量

高；约 200–400 行

后端配合

条件式 先核对 running snapshot 完整性

  • 区分正常 terminal、取消、interrupted、EOF 和可恢复断线。
  • 切会话再返回、刷新、SSE 重连都从 Canonical replay 恢复。
  • 无法证明成功时显示“结果未知/恢复失败”，不生成答案。
C2

答案状态、正式引用与 DTA

让用户一眼分清成功、失败、partial，并能验证来源和复制诊断标识。

文件范围

knowledge/index.vue、SourceChips.vue、AssistantActions.vue、新结果状态组件、Trace 路由

风险 / 体量

中；约 250–500 行

后端配合

必须补充 partial 正式语义 当前 Canonical Protocol v2 没有 partial 字段或 terminal；前端不会根据已有答案文字或长度猜测。DTA/ref 已证实。

  • 错误不再使用普通答案卡；partial 显示明确边界。
  • 来源默认摘要，按需展开，并使用稳定引用身份跳转。
  • DTA 支持复制和进入对应 Trace；绝不按时间或答案内容猜关联。
C3

typed clarification 与写入闭环

把 preview、选择、确认、提交和回执做成一个不丢状态的连续体验。

文件范围

turnProtocol.ts、knowledge/index.vue、ChatComposer.vue、新 typed interaction 组件

风险 / 体量

高；约 250–500 行

后端配合

条件式 只消费后端正式 typed payload

  • clarification.v2 按后端顺序渲染 option 和 input。
  • confirmation 只回传 option_id/confirmation_id，不回传前端 diff 正文参与提交。
  • 刷新后 pending selection 可恢复；commit receipt 是最终写入反馈。
C4

附件生命周期与范围体验

让多文件上传、绑定、失败清理和最终使用范围都可理解。

文件范围

ChatComposer.vue、attachmentAdmission.ts、knowledge/index.vue、api.ts、ConversationInfoRail.vue

风险 / 体量

中高；约 250–450 行

后端配合

条件式 精确处理范围必须来自 typed 状态

  • 展示逐文件“等待、上传、已绑定、清理中、失败”阶段。
  • 整批失败仍执行现有私有资源清理，不把未绑定资源显示成成功。
  • 删除“关键词承诺写入”的误导文案，写入只认正式预览与确认。
C5

项目、来源浏览与信息栏贯通

把对话、最近变更、当前文件、现行文档、搜索、提交和回执连成一条路。

文件范围

browser/index.vue、Overview/Search/Commit/Receipt、SourceReader.vue、ConversationInfoRail.vue、SourceChips.vue

风险 / 体量

中；约 350–700 行

后端配合

无需 复用现有正式浏览接口

  • 信息栏条目不再弹“开发中”，而是打开对应资源。
  • 空库、加载失败、无结果和权限错误分别展示并提供恢复动作。
  • 长文档、多个标题、搜索定位和小窗口阅读保持可用。
C6

响应式、性能与结构减重

在行为稳定后拆分 5,820 行主页面，删除无入口状态和重复样式。

文件范围

knowledge/index.vue、对话时间线/结果/布局组件、样式文件

风险 / 体量

高；6–10 文件，约 500–1,000 行触达，目标净删除

后端配合

无需 纯展示与结构整理

  • 窄窗口折叠侧栏与信息栏，输入区始终留在可视范围。
  • 来源和长答案按需渲染，减少 Markdown 重渲染。
  • 拆分只围绕现有 read model，不新增第二套状态。

优化前后，用户会感受到什么

最终效果不以“换了多少样式”为口径，而以状态诚实、可恢复、可验证和可诊断为口径。

06 / EFFECT

优化前

  • 断线可能看起来像结束。
  • 失败文字可能混在普通答案中。
  • 来源能阅读，但难以精确验证和跳转。
  • DTA 需要进入设置页自行寻找。
  • 右侧信息栏多处按钮只是“开发中”。
  • 多文件上传只有一个整体状态。
  • 窄窗口和超长会话的布局风险较高。
→

优化后

  • 只有正式 terminal 才显示完成。
  • 成功、失败、取消、partial、恢复中一眼可辨。
  • CanonicalRef 可展开、复制并精确打开原文。
  • DTA 就地复制，Trace 一步到达。
  • 变更、附件、文档、提交、回执互相贯通。
  • 每个附件的生命周期清晰可见。
  • 长答案、多来源和窄窗口仍保持可读。

验收口径与不可退让红线

本次不以 mock、静态数据或前端自洽为通过标准；所有动态验收由用户使用真实前后端完成。

07 / ACCEPTANCE
01实时 SSE、DB 事件和 replay 产生同一 UI read model。
02stable item revision 不重复堆积，event_id/item_id 只有一个 owner。
03非 terminal、断线、typed failure、partial 不得显示成成功。
04sources 只使用 CanonicalRef，不从答案正文或文件名猜来源。
05写入严格经过 preview、clarification、confirmation、commit。
06DTA/Trace 只能使用后端正式标识，缺失时明确报告。
07取消、切会话、刷新、重连后不串会话、不丢答案、不重复事件。
08不新增后端改动，不停止或重启后端，不改变协议含义。
本轮测量说明

根据用户要求，本方案没有运行浏览器、Computer Use、构建或前端测试，也没有主动调用接口。已静态解析用户提供的一次正式成功查询 SSE：事件结构可靠，但复制文本存在字符编码损伤。当前证据只覆盖成功查询；失败、取消、interrupted、partial、clarification、写入确认和 running replay 仍须以后续真实样本或用户实测验收，不能由本样本外推。

已识别的后端确认项

同一工具 action 的用户可见状态是 success、摘要是“完成”，但 canonical_tool_result 为 status=incomplete、has_more=true。前端开发不会擅自把它显示成 partial，也不会吞掉该差异；需要后端 owner 明确正式语义后再实现对应展示。

现有改动保护

工作树已有 electron/main.js、vibe/api.ts、SourceReader.vue、knowledge/index.vue、projectStatsPolicy.ts 修改。后续开发必须保留这些用户改动，尤其是文档数口径和 Markdown 目录修正。
